## Source event pose and browser-consumption order

- `BrowserAudioEventQueue.Enqueue` timestamps an event with `Time.time` and captures `sourceState` synchronously at the source callback; `DescribeTransform` includes world position, forward, rotation and an optional source-owned motion record. Listener selection is evaluated at that same callback and only yields a transform if exactly one enabled, active-in-hierarchy listener exists. Listener motion is therefore present only when a proven Rigidbody owns its hierarchy; no transform-delta velocity is fabricated.
- `FullSourceActorBridge.Step` calls `world.Tick` first. `RuntimeWorld.Tick` processes fixed updates, then source `Update`, coroutine advances, source `LateUpdate`, destruction flushing, and input end-frame. Only after that does the bridge drain pending audio events and construct the frame snapshot. The snapshot's `ActiveSourceStates` are thus a post-tick sample of sources that remain playing and active, while each event retains its callback-time pose. This distinguishes callback pose from end-of-frame pose, but it does not derive the correct Unity AudioSource velocity/update-mode semantics.
- In `game/index.html`, the frame consumer dispatches `audioEvents` first and then sends `audioSourceStates`, both stamped with the same frame `sourceTime`; this refreshes active source state after event dispatch. Existing audio runtime tests exercise voice playback/offset and current-state updates, but no verified Unity 2018.4 velocity fixture exists. Projectile/casing Doppler remains deferred until a version-matched native capture establishes the correct pose/velocity sampling rules.
- Reproduce this ordering from `runtime/Engine/BrowserAudioEventQueue.cs` (`Enqueue`, `ActiveSourceStates`), `runtime/Engine/FullSourceActorBridge.cs` (`Step`, `Snapshot`), `runtime/Engine/Objects.cs` (`RuntimeWorld.Tick`), and `game/index.html` frame audio calls. Any future change must preserve callback-time event timestamps and explicitly test callback pose versus post-tick state.

## Source-backed meaning versus unresolved default

Unity's 2018.4 Audio Source manual states that 3D sound settings apply proportionally to Spatial Blend, describes the Doppler, distance and rolloff controls, and defines the relationship between the blend and 3D calculations. The versioned `AudioSource.spatialBlend` API describes 0 as full 2D and 1 as full 3D. Those references establish property meaning, but do not establish the default value used when this project's serialized component omits the property.

The recovered Unity snapshot includes `ProjectSettings/ProjectVersion.txt`: `m_EditorVersion: 2017.2.0f3` (SHA-256 `3a64ae6a1c372144d8a712803efa7d89b7c39a602af3b2582b6de40b45f6cd72`). The profile scanner checks both serialized spellings `m_SpatialBlend` and `SpatialBlend`; zero of 231 AudioSource records contain either field. This establishes field absence in this profile, not Unity’s default. Keep the source adapter’s `serializedSpatialBlend` nullable: explicitly serialized values are imported and transported, while omitted values remain unknown; do not infer 0 or 1 from the missing YAML field. `Spatialize` is a plugin toggle, not the blend.

`scripts/unity_2017/AudioSpatialDefaultProbe.cs` is the bounded recovery step for this dependency. It refuses any editor other than 2017.2.0f3, creates an otherwise untouched AudioSource, runs the original prefab serializer and forced reserialization, then writes `Temp/crisis-response-audio-spatial-default-probe.json`. The report captures the API defaults, whether the serializer emitted either SpatialBlend spelling, the exact YAML SHA-256 and the complete YAML payload as base64 before deleting the temporary asset. Acceptance remains **deferred** until that report is produced on the authorized version-matched editor; the probe's existence is not evidence of the default.
