## Current implementation boundary and missing edges

- `runtime/Engine/Audio.cs` imports source fields including `priority`, `spatialize`, distance, rolloff mode/curves, pan and mixer group reference. The serialized mixer group is deserialized. The source-event queue carries source ID, clip path, time, gain, pitch, loop, mute, and priority.
- The event contract covers source-scoped Stop and `isPlaying`; browser source handles are tracked by source ID and bounded pending events. `MAX_DECODED_SOURCE_AUDIO_BYTES` bounds retained decoded source buffers, not active voices, temporary decode data, or total WebAudio memory.
- `game/weapon-audio-runtime.mjs` currently connects each decoded `AudioBufferSourceNode` through a per-event GainNode into one fixed output GainNode and compressor. Priority is carried but unused. There is no `PannerNode` or listener state. Mixer group identity, hierarchy, exposed controls, snapshot changes, DSP/effect semantics, and group-specific state are not transported to the browser. The browser test driver uses a silent mixer driver; this is not mixer parity evidence.
- Current active one-shots are tracked until `onended`; looping `Play` remains active until source-scoped Stop. Pending decode events can be delayed and source Stop cancels matching queued events. The voice manager must arbitrate across decoded active nodes and accepted pending requests, handle replacement/stop reporting, avoid leaking ended handles, and report dropped/virtualized events with source IDs. Count caps alone do not reproduce 64 real/512 virtual voices or authored priority and audibility ordering.
- The current browser output starts from an explicit gesture-unlocked AudioContext and fixed gain. Mobile suspension/restart, rapid event bursts, Safari decoding/output, and physical device output are separate acceptance requirements.
